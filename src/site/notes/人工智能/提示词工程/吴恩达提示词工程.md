## 1. 提示词工程基础：从自然语言到结构化指令

### 结构化与非结构化

- 提示词是一种**自然语言编程**。
- 结构化提示词的本质，就是通过增加约束条件，将 AI 的输出空间收敛到你想要的“航道”上。
- 优点
	- 可调试性
	- 突破模型算力瓶颈：结构化实际上是在人工分配模型的注意力权重
	- 可重复使用

### 从聊天到编程

- 随意聊天
- **精确的自然语言**
	- 追加信息
	- 不是“问问题”，而是“下指令”
	- 提示词并非越长越好，精准胜过冗余
- **结构化提示词**
	- 结构化的核心优势在于封装性与复用性。你实际上是在编写一个“函数”

### 自然语言的结构化

- 不把AI当做搜索引擎，而是刚刚入职的实习生
- 核心理念：从”提问“到”派单“
- 万能公式
	- ICIO
	- input 
		- 现有素材
		- AI生成素材
		- **给素材加一个“框”**：长文本务必使用三个引号（“”“）包裹
	- context
		- AI角色
		- 受众
		- 任务环境
		- **少样本提示**
	- instruction = 强动词 + 核心约束
		- 避免使用含义模糊的词汇（处理、优化），而是给出明确的执行路径的**强动词**
		- 核心约束（好的指令是收敛）
		- 慢思考（**CoT (Chain of Thought) 技术**）：“请一步步思考”
	- output

### 底层逻辑

1. **概率空间的收敛**
	1. 大语言模型本质是一个基于概率的文字接龙游戏
	2. 提示词工程的目标就是提供约束条件，将AI的无线概率空间，收敛到你想要的那个唯一确定结果
2. **信噪比与注意力**

## 2. 提示词工程进阶：引导AI进行思考

### 2.1 格式突破：Meta-Prompting——利用AI写出好的提示词

- 冷启动难题：面对空白输入框不知道写什么
- 使用下方提示词专家模板
	- 你是甲方，提供自然语言的核心意图
	- AI是乙方，编译成完美的结构化指令
- 跨模型写作
	- Claude对提示词的质量非常敏感，高质量的结构化提示词可以获得完全不同的表现
	- 可以利用反应快，逻辑好的AI作为跳板生成优化后的prompt

> 	 • 增强逻辑性的建议：你可以考虑将问题拆分成更小的部分，帮助 LLM 更好地掌握你的逻辑。

### 2.3 逻辑突破：思维链（CoT）和思维树（ToT）

- 痛点：AI的思维模式可以分为两种，AI本质上是概率预测及其，默认是快思考状态
	- 快思考：依赖直觉，快速但是容易出错
	- 满思考：逻辑推演，缓慢但是准确
- 思维链：**Give the Model Time to Think**
	- **Zero-Shot CoT*：：“让我们一步步思考”
	- **Meta-CoT**：显式指定每一步的推理顺序，解决复杂任务中逻辑跳步的问题，中间生成的文字就是模型的草稿
- 内心独白
	- 痛点：**顺从性幻觉**，AI符合用户的预设立场而不是客观分析。用户的偏见会污染AI
	- 方案：强制自主推导
		- 盲测与独立分析
		- 偏差对比
		- 修正输出
```c

...[文章内容]...

这篇文章是不是在暗讽我们的产品策略很失败？ 
System Instructions: 你是一个客观公正的分析师。为了避免被用户的误导，请务必执行以下管道：
# Processing Pipeline 
	1. Step 1: 盲测与独立分析 在 标签内，暂时屏蔽用户的 query。 
	2. Step 2: 偏差比对 
	3. Step 3: 修正输出 仅基于

的客观文本，提炼其核心论点和情感倾向。建立你自己的“客观评价基准”。 将你的“客观评价”与用户的进行比对。判断用户的预设观点是否与事实相符。 在 标签内回答用户。如果用户的预设是错误的，请利用Step 1 中的证据进行温和 但坚定的纠正
```

### 2.4 解决语言风格、幻觉挑战：Few-Shot 与 Step-Back

- 少样本提示：精确校准
	- 原理：当你提供一系列具有固定模式的范例时，模 型不再是去“理解”你的指令，而是在进行类比推理
	- 我的样本从哪里来？——用AI训练AI
- 后退提示：深度抽象
	- 思路：先搜索原理，再动手执行

## 3. Gem封装：指令集与语境的实体化

### 3.1 封装原理

![Pasted image 20260305083742.png](/img/user/Pasted%20image%2020260305083742.png)
- 聊天流程缺点
	- 指令衰减：最早的指令权重最低
	- 遗忘机制
- GEM封装构成
	- 内核层：SystemInstructions（核心身份、约束、逻辑）
	- 配置层：知识库（KnowledgeBase）、工具（Tools）和少样本（Few-Shot）
	- 交互层
- 本质：函数
	- 编写函数体（Gem）
	- 函数调用和传参
- 使用原则
	- Payload Only 原则：拒绝冗余定义的“零上下文交互”
		- ICIO公式中，CIO已经存在于系统层
		- 我们应该只输入Input（Payload，有效负载）
	- 角色一致性协议：严禁Role Conflict
	- 原子化任务流
		- 不要让之前的对话变成下一次任务的噪声
- 何时封装？
	- 复用性
	- 确定性
	- 效率性

- Meta构建（ETL过程）

	- ICW架构：
		- Identity

#### Knowledge

- 别把AI算力浪费在OCR上
	- PDF：信噪比高，浪费计算资源
	- Word / TXT：缺少明确的逻辑层次标记
	- Markdown：纯粹的语义载体
- GIGO原则：垃圾进，垃圾出
- 知识挂载：ETL流程
	- E：数据获取，文字版PDF
	- T：格式转换，MinerU
	- L：数据清晰，用AI智力AI，创建一个临时的数据清洗Gem
#### 工具集

- 挂载Deep Research、Canvas、Banana 以及 Veo 等原生插件
### 3.3 Gem的调优与动态逻辑

- 优化1：动态变量插槽：单体复用
	- 痛点：例如，为了面试Java岗 位写一个Gem，为了面试Python 岗位又写一个 Gem。这种做法会导致系统指令维护 困难：一旦你需要调整面试逻辑，就不得不逐个修改十几个Gem
	- 原理：将Prompt视为“模板字符串”，而非静态文本。通过 在System Instructions 中预埋“占位符”，我们可以在运行时根据用户的输入动态注入 具体的参数
	- 方法
		- 提示词中预留好变量
		- 填槽
			- 首条输入
			- 配置指令
- 优化2：多用途Gem
	- Switch结构：明确支持哪几种工作流，定义激活每种模式的关键词或者语义特征
- 优化2：元数据标记法
	- 痛点：知识库更新
	- 解决：增量补丁文件
	- 流程
		- 增加补丁文件
		- 定义权重等级
